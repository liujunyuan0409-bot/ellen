# 五感月度销售表

## Overview
从戴维盈动商家后台按月取四份数据——「销售汇总」商品级明细、「营业报表」逐日经营数据、「余额统计」余额流水、当月 ≥1 万的已支付订单——按 `rules.yaml` 清洗成 **分类 → 商品 → 规格** 三层表，写进**当年的年度文件** `~/Desktop/Ellen/五感专题分析/YYYY年五感销售数据统计.xlsx`（一年一个文件，不存在就停止；用户确认后才用 `--create` 新建；用户把五感相关文件都收在这个文件夹，备份在其下 `_backup/`）。
同文件夹里的其他「五感销售数据统计」文件（如 2025 年手工版）只读不写，但新品识别会参考。
**口径只认 `rules.yaml`**；脚本对不平、遇到没登记的规格选项会直接停下，不要绕过。

## 已验证的口径（2025-08 ~ 12 与手工表逐行对平）
| 表列 | 接口字段 | 说明 |
|---|---|---|
| 实际销量 | `real_num` | |
| 实际销售额(不含退款、优惠) | `real_total` | = 销售总额 − 优惠 − 退款 |
| 单价 | `one_price` 均值 | 后台标价在明细行上的算术平均，不是销售额/销量 |
| 规格 | `key_list` 过滤 | 只保留 `spec_rules.keep`（意式：咖啡豆；周边：颜色） |

取数条件 = 销售汇总页默认：**支付时间**（`time_type=2`）、整月、全时段、不拆套餐、不合并同名。

## 运行前检查（v0.2.0）
- 使用提供可执行页面脚本的 Playwright MCP `browser_evaluate`，先确认工具已加载；只读 DOM evaluate 不能代替。若缺失，先配置并重新加载工具，不要读取浏览器资料或导出 token 绕过。
- 在目标后台执行 `scripts/browser_probe.js`，用 `filename` 保存 `.playwright-mcp/wugan_browser_probe.json`。它只返回能力、站点和登录布尔值，不返回凭证。工具拒绝执行即视为能力不支持。
- 用运行报表的同一个 Python 执行：
  ```bash
  python -I scripts/preflight.py --month YYYY-MM --browser-check <probe.json>
  ```
  检查 Python 依赖、后台登录、年度文件是否可读。默认位置读取 `config.json`，可用 `--dir` / `--workbook` 覆盖；检查和写入必须使用同一路径。目录不存在不自动创建；新年度文件须用户确认后，在检查及写入命令中添加 `--create`。
- 依赖为 `openpyxl`、`pyyaml`。优先使用项目虚拟环境；缺失时在该环境运行 `python -m pip install openpyxl pyyaml`，不要假定系统 Python 已安装。

## 流程
1. **确定月份**：默认上一个完整自然月；sheet 名 `YYYY年M月`。
2. **登录**：Playwright `browser_navigate` 到 `https://zhyx.eingdong.com/console/#/login`。如果没有跳到 `#/index`，**停下请用户在浏览器里登录**（不要索要或保存账号密码）。
3. **取数**：读 `scripts/fetch_month.js`，把所有 `__MONTH__` 替换成 `YYYY-MM`，整段作为 `browser_evaluate` 的 function，`filename` 存到 `.playwright-mcp/wugan_raw_YYYY-MM.json`（Playwright 只能写到它允许的目录）。四个接口检查 HTTP、业务状态和列表结构；销售、余额、订单自动有界分页，日报校验整月。结果带 `fetch_meta` 完整性记录。结果里有 `error` 就停止，不以空数据继续，按提示处理（`NOT_LOGGED_IN` → 回第 2 步）。返回内容只含统计字段，不含顾客昵称、手机号、用户 ID。
4. **试跑**：
   ```bash
   python -I scripts/build_report.py --raw <raw.json> --dry-run   # 文件按 raw 的年份自动定位；--dir 改目录
   ```
   需要 `openpyxl` 和 `pyyaml`。
   - 退出码 2 `UNKNOWN_SPEC_OPTIONS`：把列出的选项给用户看，按用户意见补进 `rules.yaml` 的 keep/drop 后重跑。明显属于冰量/浓度/奶/尺码/克重的可以直接归 drop，但要在回复里列出来。
   - 退出码 3 `RECON_FAIL` 或 `VALIDATION_FAIL`：**不出表**，排查月份、完整性、余额对数或文件状态；不可绕过校验。
   - 退出码 5 `ANOMALY_PENDING`：当月有单笔 ≥ 1 万的已支付订单或余额「商家扣除」还没确认。**把清单原样给用户看，由用户判断是不是真实消费**，不要自己猜。
     对扣除，要一起查同一账户前后的充值（余额统计 → 余额流水）：如果是「充值 → 几天后被商家等额扣回」，按成对记录整组剔除。
     确认结果写进 `rules.yaml` 的 `anomaly.excluded_orders`、`excluded_balance_pairs` 或 `kept`，只记时间和金额（仓库是公开的，不写用户信息）。
   - 摘要里的「新商品 / 新分类」：问用户要不要改名或改分类（写进 `product_rename` / `reclassify`）。新品 = 同目录所有年度文件里**此前月份**没出现过；补历史月份时按月份从早到晚依次写入，否则新品会被多报。
5. **写入**：去掉 `--dry-run` 再跑一次。先在同目录写临时文件并回读，核对工作表、经营数据、明细与错误单元格；验证通过后备份到 `_backup/`，用原子替换发布。源文件处理中有变化会停止，失败不覆盖原文件。同步记录版本、规则/raw/输入输出文件 SHA256、备份和资金对数到 `_backup/*.audit.json`（prepared 表示待确认，committed 表示已发布）；不记录凭证。新增三个 sheet：当月主表、`-1元计价`、`-异常与调整`，并按月份自动排好顺序；同时更新「月度经营数据」（订单数、新老客单、储值、订单实收，都已剔除异常）；第一页「年度汇总」（经营指标：订单数/日均单/客单价/件单价、老客单占比、储值充值/余额消费/月末余额、订单实收/现金流入；以及分类 × 月份的销售额/销量）每次写入都会从各月主表重建。只想重建汇总用 `--summary-only <年度文件>`。sheet 已存在时退出码 4，只有用户确认后才加 `--replace`。
6. **回复用户**：主表总额、1 元计价金额、和上月比较、异常与调整的要点。

## rules.yaml 各项
- `spec_rules`：哪些分类展开规格，保留哪些选项
- `spec_rename` / `product_rename` / `reclassify`：人工统一名称和分类，每次命中都会记到「异常与调整」
- `one_yuan_price_max`：0 < 标价 ≤ 阈值的商品（补差价、1 元「手冲咖啡」）不进主表，**主表占比分母不含这部分**
- `category_order`：主表分类排序
- `anomaly`：大额消费的确认结果。`excluded_orders` 剔除的订单；`excluded_balance_pairs` 成对剔除的「充值 → 商家扣回」，充值写到账 `amount` 和实付 `paid`（营业报表「储值充值」是实付口径，剔除时扣 `paid`）；`kept` 确认为真实消费的大额

## 常见坑
- **大额充值是正常的，大额消费要核实**：2025-10 有两笔店员后台下的补差价（37,131、38,285 元），另外有三组「充值后被商家等额扣回」（2025-09 退还 36,000、2026-03「消费」29,104、2026-08「结算」20,000），都已经由用户确认剔除。商家扣除不一定进入营业报表「收银」（2026-10 的充值退款就未进入），不能无条件从收银消费再次扣减。
- 营业报表的「储值充值」是实付金额，不含赠送；余额流水里的充值含赠送。所以月末余额 ≠ 累计（充值 − 消费），不要在表里放「储值净增」。
- **补差价按 1 元计价，销量 = 金额**：2025-10 一项就是 75,884 件。放进主表会把销量和占比全部扭曲，所以单独放一个 sheet。
- **标价 0 的是赠品**，留在主表；成交 0 元的行（100% 优惠）会列在「异常与调整」里。
- **后台页面顶部的「实际销售额」可能和明细加总差几十元**（退款归属不同），表格以明细为准，差额写在「异常与调整」。
- 不要用透视表的「求和」算单价（2025-11 手工表就是这样错的），也不要换成销售额/销量。
- 销售/余额分页以 total_count 对齐，订单无 total_count 时继续直到不足 100 条；最多 100 页，重复页、总数变化或达到上限直接失败。订单列表接口单次最多查 3 个月。接口忽略分页参数时不得只用第一页出表。
- **成对剔除充值要扣实付，不是到账**：2026-03-08 那 4 笔每笔到账 7,276，其中赠送 388、实付 6,888；按到账扣会把 3 月储值充值少算 1,552。新增成对记录时，用当天营业报表的 `topup_total` / `topup_gift` 反推 `paid`。
- 订单实收（营业报表：订单额 − 退款）和商品销售额（销售汇总）个别月份差几十到一百多元（2026-01 差 148、2026-06 差 99），其余月份完全一致；推断是退款跨月归属不同，两者以各自口径展示即可。
- 这个仓库是公开的：raw json 和工作簿**不要提交**，token 只在浏览器里用。

## 资金对数与回归
- 以分核对余额统计：期初 + 增加 − 扣减 = 期末；余额流水分类加总必须与统计一致；购买商品 − 订单退款须与营业报表净余额支付一致。未知非零流水类型停止人工核实，不擅自归类。
- 余额消费优先用流水扣减 − 订单退款 − 已确认异常扣除，避免充值退款重复扣减。旧 raw 的回退计算仅供兼容；新写表必须通过完整余额校验。
- 每组剔除的充值到账合计必须等于扣回金额，当月记录必须实际存在；储值充值仍按 paid 剔除，不按含赠送的到账金额剔除。
- 修改脚本后运行 `python -I scripts/test_reliability.py` 和 `node scripts/test_fetch.mjs`。真实数据仅在仓库外的临时副本试跑，正式年度表不用于开发测试。
